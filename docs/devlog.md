> 이 섹션은 2026-11-02에 1일 차를 되돌아보며 정리한 것이다. 당일 기록이 아니라서 원인·증상의 세부 중 일부는 일반적인 원인으로 추정해 적었다(확인하지 못한 것은 본문에 그렇게 표시). 당시 숫자가 남아 있지 않은 곳은 비워 두었다. 키 값은 어디에도 적지 않았다.

### A. 개발 환경

#### 1. PowerShell에서 npm 실행 시 보안 에러
- **발견한 문제**: PowerShell에서 npm을 실행하면 스크립트 실행 보안 에러가 났다.
- **원인**: Windows PowerShell의 스크립트 실행 정책이 막고 있었다.
- **내가 내린 판단과 요청**: 컴퓨터 전체가 아니라 내 계정에서만 실행을 허용하기로 했다.
- **해결 방법**: 실행 정책을 현재 사용자 범위에서 `RemoteSigned`로 변경.
- **결과**: npm이 정상 실행됨.
- **배운 점**: 정책은 범위를 좁혀서(현재 사용자) 푼다. 서명된 스크립트만 허용하는 `RemoteSigned`면 개발에 충분하다.

#### 2. Claude Code 설치 스크립트가 반응 없음
- **발견한 문제**: 설치 스크립트를 실행했는데 아무 반응이 없었다.
- **원인**: 설치 스크립트가 이 환경에서 동작하지 않았다. (정확한 원인은 확인하지 못함)
- **내가 내린 판단과 요청**: 원인을 파고들기보다 다른 설치 경로를 쓰기로 했다.
- **해결 방법**: npm으로 설치하는 방법으로 변경.
- **결과**: 설치 완료.
- **배운 점**: 한 방법이 막히면 원인 추적에 시간을 쓰기 전에 같은 결과를 내는 다른 경로가 있는지 본다.

#### 3. git이 인식되지 않음
- **발견한 문제**: `git` 명령을 찾지 못했다.
- **원인**: Git이 설치되어 있지 않았다.
- **내가 내린 판단과 요청**: Windows용 표준 도구를 설치.
- **해결 방법**: Git for Windows 설치.
- **결과**: git 사용 가능(저장소 clone 등은 5번에서 진행).
- **배운 점**: 개발 도구는 설치 여부부터 확인한다.

#### 4. 설치 후에도 명령어를 찾지 못함
- **발견한 문제**: 설치를 마쳤는데 같은 터미널에서 명령어를 여전히 찾지 못했다.
- **원인**: 이미 열려 있던 창은 설치 전의 환경 변수(PATH)를 그대로 가지고 있어서 새 프로그램을 모른다.
- **내가 내린 판단과 요청**: 설치가 잘못됐다고 보기 전에 창을 새로 열어 확인하기로 했다.
- **해결 방법**: 터미널 창을 닫고 새로 열기.
- **결과**: 명령어 인식됨.
- **배운 점**: 설치 직후 "명령어를 찾을 수 없음"이면 먼저 창을 새로 연다. 재설치는 그다음이다.

#### 5. OneDrive 한글 경로에서 폴더 생성 실패 (ENOENT)
- **발견한 문제**: 프로젝트가 OneDrive 아래 한글이 들어간 경로에 있었고, 폴더를 만드는 데 `ENOENT` 오류가 났다.
- **원인**: OneDrive 동기화 폴더와 한글 경로의 조합에서 도구가 경로를 제대로 다루지 못했다. (정확한 내부 원인은 확인하지 못함)
- **내가 내린 판단과 요청**: 경로를 어떻게든 우회하기보다, 작업 위치 자체를 옮기기로 했다.
- **해결 방법**: `C:\dev`로 저장소를 다시 받았다(clone). 이후 프로젝트는 `C:\dev\gangnam-latenight-map`에서 작업한다.
- **결과**: 폴더 생성 오류 없이 작업 진행.
- **배운 점**: 개발 프로젝트는 동기화 폴더나 한글·공백 경로를 피해 짧은 영문 경로(`C:\dev`)에 둔다.

#### 6. AI가 보안 우회를 시도했고 자동 모드가 막음
- **발견한 문제**: 5번을 해결하는 과정에서 AI(Claude Code)가 보안 장치를 우회하는 방법을 시도했고, 자동 모드가 그 시도를 막았다.
- **원인**: AI가 오류를 빨리 없애는 쪽으로 움직여, 권한 제약을 돌아가는 수단을 골랐다.
- **내가 내린 판단과 요청**: 우회를 허용하지 않고, 경로를 옮기는 정공법을 선택했다.
- **해결 방법**: 우회 없이 5번의 `C:\dev` 이전으로 해결.
- **결과**: 보안 설정 변경 없이 문제 해결.
- **배운 점**: 막힌 것을 돌아가려는 제안은 "왜 막혀 있는지"부터 묻는다. 자동 모드와 권한 확인은 이런 때를 위한 안전장치라서 끄거나 피하지 않는다.

### B. 코드·데이터

#### 7. README 한글 깨짐
- **발견한 문제**: README의 한글이 깨져 보였다.
- **원인**: 파일 인코딩이 UTF-8이 아니었다.
- **내가 내린 판단과 요청**: 깨진 글자를 고치기보다 처음부터 다시 쓰기로 했다.
- **해결 방법**: UTF-8로 README를 다시 작성.
- **결과**: 한글 정상 표시.
- **배운 점**: 한글 문서는 저장 인코딩을 UTF-8로 맞춘다. (Windows에서는 도구마다 기본 인코딩이 달라질 수 있다.)

#### 8. 카카오 검색 45개 제한
- **발견한 문제**: 카카오 카테고리 검색은 한 번에 최대 45개(15개 × 3페이지)까지만 돌려준다. 강남역 반경 1km에는 훨씬 많은 가게가 있다.
- **원인**: API가 한 검색의 결과 수를 제한한다.
- **내가 내린 판단과 요청**: 반경을 줄이거나 포기하지 않고, 영역을 쪼개서 모두 수집하기로 했다.
- **해결 방법**: 영역을 사각형으로 나눠 검색하고, 결과가 45개에 닿으면 4등분해서 다시 검색(`scripts/collect_places.py`).
- **결과**: API 호출 230번으로 가게 **2,513개** 수집. 쪼개도 45개를 넘어 **잘린 영역은 0곳**.
- **배운 점**: 결과 수에 상한이 있는 API는 "상한에 닿았는지"를 검사해서 닿으면 더 잘게 나눈다. "잘린 영역 0곳"이라는 검증 숫자를 남겨 두면 누락이 없다는 근거가 된다.

#### 9. 지도 말풍선이 계속 쌓임
- **발견한 문제**: 마커를 누를 때마다 말풍선이 닫히지 않고 쌓였다.
- **원인**: 열려 있는 말풍선을 기억하지 않아서, 새로 열 때 이전 것을 닫지 못했다.
- **내가 내린 판단과 요청**: 말풍선은 한 번에 하나만 보이게 하기로 했다.
- **해결 방법**: 열린 말풍선을 변수에 기억해 두고, 새 말풍선을 열기 전에 닫도록 수정(`static/js/map.js`).
- **결과**: 한 번에 하나만 표시됨.
- **배운 점**: 지도 위 팝업류는 "현재 열린 것"의 상태를 하나 들고 있어야 한다.

#### 10. 카카오 JS 키 끝에 'v'가 붙음
- **발견한 문제**: 키를 `.env`에 저장하는 중에, 카카오 JS 키 끝에 `v`가 하나 더 붙어 있는 것을 발견했다. 지도가 안 뜨는 오류가 나기 전에 미리 잡았다.
- **원인**: 키를 복사해 붙여넣을 때 끝에 글자가 섞여 들어갔다(붙여넣기 실수). 처음 추측은 따로 없었다. 저장 과정에서 값의 끝을 확인하다 발견했다.
- **내가 내린 판단과 요청**: 키가 틀렸다고 재발급하기 전에, 붙여넣은 값부터 살펴보기로 했다.
- **해결 방법**: 저장하면서 끝의 `v`를 제거.
- **결과**: 잘못된 키로 지도를 불러오는 일 없이 해결. 지도는 정상 표시됨.
- **배운 점**: 키를 저장할 때는 붙여넣은 값의 앞뒤를 확인한다. 인증 오류가 나면 키가 틀렸다고 단정하기 전에 값부터 본다. 키 값은 문서에 적지 않는다.

#### 11. 카카오 도메인 등록 위치 혼동
- **발견한 문제**: 카카오 개발자 콘솔에서 `localhost:5000`을 어느 도메인 칸에 등록해야 하는지 헷갈렸다.
- **원인**: 콘솔에 도메인을 등록하는 곳이 여러 군데 있고 이름이 비슷하다.
- **내가 내린 판단과 요청**: 지도를 쓰는 건 JavaScript 키이므로 거기에 맞는 항목에 등록하기로 했다.
- **해결 방법**: JavaScript SDK 도메인에 `localhost:5000` 등록.
- **결과**: 로컬에서 지도 로딩됨.
- **배운 점**: 키 종류(JavaScript / REST)마다 도메인 등록 위치가 다르다. 쓰는 키에 맞는 설정인지 먼저 확인한다.

#### 12. REST 키를 외부 채팅에 붙여넣음
- **발견한 문제**: 카카오 REST 키를 외부 채팅에 붙여넣었다.
- **원인**: 키를 보여줘서는 안 되는 비밀 값으로 다루지 않고 값을 그대로 공유했다.
- **내가 내린 판단과 요청**: 이미 노출된 키는 되돌릴 수 없으니 폐기하기로 했다.
- **해결 방법**: 그 키를 삭제하고 재발급. 이후 키는 `.env`에만 보관하고(`.gitignore`로 깃에서 제외) 코드·문서에는 적지 않는다.
- **결과**: 노출된 키는 무효화됨. 새 키는 `.env`에만 있다.
- **배운 점**: 외부에 노출된 키는 "쓰지 않았으니 괜찮다"가 아니라 즉시 폐기하고 재발급한다. 키는 `.env`에만 둔다. 11/2 구글 키도 재발급함: 새 키로 교체(Rotate), 조회 테스트 2건 성공, 예전 키 삭제. (구글 키도 대화에 붙여넣은 일이 있었다.) 키 값은 적지 않는다.

### C. AI 제안을 바꾼 판단

#### 13. 구글 조회 대상에서 카페를 빼자는 제안
- **발견한 문제**: 구글 조회 비용을 줄이려는 AI 제안이 카페를 조회 대상에서 빼는 것이었다.
- **원인**: 비용·무료 한도만 기준으로 대상을 정해서, 프로젝트의 출발점이 빠졌다.
- **내가 내린 판단과 요청**: 이 프로젝트의 출발점은 학원이 끝나고 밤늦게 공부할 곳을 찾는 것이다. 카페를 빼면 목적이 사라진다고 판단해 카페를 포함하게 했다.
- **해결 방법**: 카페 333개를 강남역에서 가까운 순으로 포함하고, 총 900개로 맞췄다(`scripts/select_scope.py`).
- **결과**: 조회 범위 900개 = 이름 기준 1 + 심야 업종 293 + 술집 273 + 카페 333. 무료 한도 안.
- **배운 점**: 비용 최적화는 목적을 지키는 안에서 한다. AI의 효율적인 제안도 "내 출발점에 맞는가"로 되묻는다.

#### 14. 심야 기준 새벽 2시 제안
- **발견한 문제**: AI가 심야의 기준을 새벽 2시로 제안했다.
- **원인**: 일반적인 심야 기준으로 정해서, 내 사용 상황이 반영되지 않았다.
- **내가 내린 판단과 요청**: 학원이 밤 12시에 끝나므로 자정 이후까지 여는 곳이면 쓸모가 있다고 판단해 기준을 자정으로 바꾸게 했다.
- **해결 방법**: 심야 기준을 "마감이 자정(00:00) 이후"로 변경. 정확히 자정에 닫는 곳은 심야가 아니다. 기준 시각은 스크립트 상수(`LATE_NIGHT_AFTER_MIN`)로 둬서 바꿀 수 있게 했다.
- **결과**: 기준이 넓어져서 심야 가게와 이후 반려동물 판별 대상이 늘어난다(구글 조회 결과가 나오면 개수 확인).
- **배운 점**: 기준값은 내 생활 패턴에서 나온다. 일반 기준보다 사용 상황을 우선하고, 바꿀 수 있게 상수로 둔다.

#### 15. 반려동물 판별에 유료 AI API 제안
- **발견한 문제**: AI가 반려동물 여부를 판별하려면 유료 AI API를 쓰자고 제안했다.
- **원인**: 자동화하기 가장 쉬운 방법을 골랐고, 추가 결제가 든다.
- **내가 내린 판단과 요청**: 추가 비용을 쓰지 않기로 했다. 네이버 검색 결과를 모아 두면 Claude Code가 대화로 직접 읽고 판별하게 한다.
- **해결 방법**: 스크립트는 검색 결과 수집만 하고, 판별은 Claude Code 세션에서 약 20개씩 끊어서 한다. 결과는 파일에 저장해 이어서 할 수 있게 한다(`docs/plan.md` 4장).
- **결과**: 추가 결제 없음. 대신 수작업 단계가 생기고 Claude Code 사용량이 든다. 결과는 "AI 추정"으로 표시.
- **배운 점**: 자동화와 비용은 맞바꾼다. 데이터가 한 번 만들어지면 되는 작업은 수작업 단계를 받아들이고 비용을 아끼는 선택이 맞을 수 있다.

- **원인**
  - 처음 추측: 이름 유사도 기준(0.5)이 너무 엄격해서 같은 가게를 놓쳤다. (특히 이방인혼술바, 로우커피스탠드)

    |---|---|---|---|
    | 이방인혼술바 서울강남역점 | 이방인 혼술바 서울 강남점 | 784m | 다른 지점(또는 카카오 좌표 오차 가능성) |

## 2026-11-02 #6. 기본 동작을 "아무것도 조회하지 않음"으로 변경

- **날짜**: 2026-11-02
- **발견한 문제**: #4의 남은 허점. 인자 없이 `fetch_google_hours.py`를 실행하면 시험 조회 20건이 나가, 목록만 보려는 실행도 과금 호출이 될 수 있었다.

- **해결 방법**: `--limit` 기본값을 없앴다(None). `--limit N`, `--limit 0`, `--retry` 중 하나를 줘야만 조회한다. `--approve`/`--reject`는 캐시만 고치고, 승인 시 영업시간이 없는 건에만 1건씩 조회한다. 인자 없이 실행하면 "조회 인자가 없어 아무것도 조회하지 않습니다"를 출력하고 호출 0건으로 끝난다. `--max-calls` 상한은 그대로 둔다.
- **결과 숫자**: 인자 없는 실행 호출 0건 확인. `--approve ... --reject ... --max-calls 3` 실행 호출 3건(승인 3건의 영업시간 조회).
- **배운 점**
  - 과금되는 도구의 기본값은 "안전한 쪽"(아무것도 안 함)으로 둔다. 실행하려면 의도를 인자로 밝히게 한다.
