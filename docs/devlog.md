## 2026-11-02 #1. 구글 매칭 시험 20개 중 5개 실패

- **날짜**: 2026-11-02
- **발견한 문제**: `fetch_google_hours.py` 시험 20개 중 5개가 구글에서 같은 가게를 찾지 못함(`no_match`). 실패율 25%. 이대로 900개를 돌리면 약 200개가 `확인 필요`로 남을 것으로 예상됨.
- **원인**
  - 처음 추측: 이름 유사도 기준(0.5)이 너무 엄격해서 같은 가게를 놓쳤다. (특히 이방인혼술바, 로우커피스탠드)
  - 실제 원인: 이름을 완화해도 결과가 같았다. 구글 후보와의 거리를 보니 784m~8.8km 떨어진 다른 지점이거나, 구글에 없는 가게였다.

    | 가게 | 구글 후보 | 거리 | 판정 |
    |---|---|---|---|
    | 이방인혼술바 서울강남역점 | 이방인 혼술바 서울 강남점 | 784m | 다른 지점(또는 카카오 좌표 오차 가능성) |
    | 마리짱 신논현역점 | 마리짱 | 732m | 다른 지점 |
    | 로우커피스탠드 강남점 | 로우커피스탠드 | 약 5.8km | 다른 지점 |
    | 예향 | 예향 | 1.7~8.8km | 다른 지점 |
    | 청년쥬스 | (비슷한 이름 없음) | - | 구글에 없음 |
- **내가 내린 판단과 요청**: 실패로 두는 게 맞다고 판단함. 이름 규칙을 완화하되 거리 조건을 같이 두고, 애매한 건 목록으로 모아 직접 확인하겠다고 요청함.
- **해결 방법**: 5건을 이름 완화 규칙으로 다시 조회했고, 결과가 그대로 `no_match`임을 확인했다. 실패로 유지. 후보별 거리·유사도를 캐시에 남기게 해서 실패 원인을 나중에도 볼 수 있게 함.
- **결과 숫자**: 재조회한 5건 → 5건 모두 매칭 실패 유지(이름은 일치, 거리가 멀어서 실패 또는 구글에 없음).
- **배운 점**
  - 이름이 같다고 같은 가게가 아니다. 프랜차이즈는 지점이 많아서 거리를 같이 봐야 한다.
  - "기준이 너무 엄격하다"는 추측은 후보의 거리·유사도 값을 확인하기 전에는 믿지 말 것. 실패 후보를 저장해 두면 추측 대신 확인할 수 있다.

## 2026-11-02 #2. 매칭 규칙 개선 (확정 / 검토 / 실패 3단계)

- **날짜**: 2026-11-02
- **발견한 문제**: 이름·거리 기준이 하나뿐이라, 같은 가게인데 표기가 달라 놓치는 경우(레이지요거트, 라운지엑스 24h, 스탑오버)와, 다른 지점인데 통과하는 경우(마리김밥 78m)를 구분하지 못함.
- **원인**
  - 처음 추측: 이름 비교만 손보면 된다.
  - 실제 원인: 문제가 두 방향이었다. 이름 비교가 엄격해서 놓치는 것(표기 차이: 영문 병기, 지점명 유무)과, 거리 조건이 느슨해서 틀린 짝을 만드는 것(100m 이내면 통과)이 함께 있었다.
- **내가 내린 판단과 요청**: 이름에서 지점명·공백을 빼고 비교하되, 엉뚱한 가게와 짝지어지지 않게 거리 조건을 같이 둘 것. 애매한 경우는 목록으로 모아 직접 확인. 20m 이내면 유사도가 낮아도 검토 목록에 넣되 자동 승인은 하지 않을 것.
- **해결 방법** (`scripts/fetch_google_hours.py`)
  - 이름 비교에서 공백·괄호·지점명("서울", "강남역", "본점", "~점" 등)을 뺀다.
  - 포함 관계는 짧은 쪽이 긴 쪽에서 차지하는 비율로 점수를 매긴다. (예향 vs 예향정 = 0.67)
  - 3단계로 분류한다.

    | 등급 | 조건 | 처리 |
    |---|---|---|
    | 확정 | 유사도 0.8 이상, 50m 이내 | 자동 반영 |
    | 검토 | 유사도 0.8 이상 150m 이내 / 유사도 0.6 이상 50m 이내 / 20m 이내(유사도 무관) | 영업시간은 받되 승인 전에는 반영하지 않음 |
    | 실패 | 위에 해당 없음 | `확인 필요` |
  - 검토·실패·영업시간 없음·폐업 건을 `data/raw/review_matches.json`에 모은다. `--approve`로 승인한다.
  - 20m 이내 규칙은 이미 `no_match`로 저장된 건에도 후보 거리 기록으로 소급 적용했다. 영업시간은 승인할 때 1건씩 조회한다.
- **결과 숫자** (캐시 40건 기준)
  - 정상 15 / 검토 9 / 영업시간 없음 7 / 매칭 실패 7 / 폐업 2
  - 검토 9건 중 승인 3건, 대기 6건(마리김밥 1건 + 20m 이내 근접 후보 5건).
  - 20m 근접 후보 5건 중 실제 같은 가게로 보이는 것은 레이지요거트, 라운지엑스 24h, 스탑오버. 옵션스페셜티커피 서초동아타워점 → 카페베네강남동아타워점(8m), 강다짐 강남역지하상가점 → 더벤티 강남역지하상가점(4m)은 다른 가게다.
  - 개선 후 실패율: **확인 후 기입** (전체 900개 조회 후 계산)
- **배운 점**
  - 거리가 매우 가까운 후보는 이름이 달라도 검토할 가치가 있지만, 같은 건물의 다른 가게가 섞여 들어온다. 그래서 20m 규칙은 자동 승인이 아니라 검토 목록으로만 보낸다.
  - 기준을 바꿨을 때 이미 받은 결과를 API 호출 없이 다시 분류할 수 있게 해 두면 비용이 들지 않는다.

## 2026-11-02 #4. 요청하지 않은 API 호출이 실행됨

- **날짜**: 2026-11-02
- **발견한 문제**: "실패한 5건만 다시 조회"를 요청했는데, 그보다 많은 호출이 나갔다. 요청 범위를 넘은 호출이 약 20건(Text Search 약 30건, Details 약 13건).
- **원인**
  - 처음 추측: (해당 없음. 실행 직후 로그에서 바로 확인됨)
  - 실제 원인 (Claude Code의 실수 2가지)
    1. 재조회 결과 파일이 저장되지 않는 것을 확인하려고 `--retry`를 한 번 더 돌려 같은 5건이 2번 조회됨.
    2. 목록 파일을 만들려고 인자 없이 스크립트를 실행했는데, 인자 없는 기본 동작이 "새 가게 20개 시험 조회"여서 의도하지 않은 20개가 조회됨.
- **내가 내린 판단과 요청**: 요청한 범위만 호출할 것, 추가 호출이 필요하면 먼저 건수를 물어볼 것, 스크립트에 최대 호출 건수 제한을 둘 것.
- **해결 방법**
  - 스크립트: 실행당 API 호출 상한 `--max-calls`(기본 40건)을 넣었다. 상한에 닿으면 중단한다. 실행 끝에 이번 호출 건수를 출력한다. 승인(`--approve`)은 조회 없이 캐시만 고치고, 영업시간이 없는 건에만 1건씩 조회한다. 전체 900개를 돌리려면 `--max-calls`를 명시적으로 올려야 한다.
  - 작업 방식: 요청 범위를 넘는 API 호출이 필요하면 먼저 건수를 말하고 확인받는다.
  - 남은 허점: 인자 없이 실행하면 여전히 시험 20개를 조회한다. → #6에서 기본 동작을 "아무것도 조회하지 않음"으로 바꿔 해결.
- **결과 숫자**
  - 추가 호출: Text Search 약 30건, Details 약 13건 (무료 한도 Text Search 5,000건, Details 1,000건 안)
  - 이 시점 캐시: 40건 (시험 20 + 의도치 않은 추가 20)
  - 실제 청구 금액: **확인 후 기입** (Google Cloud 콘솔 청구 내역 확인 필요)
- **배운 점**
  - 데이터를 볼 목적의 실행이 호출을 동반하지 않도록, 조회와 보기를 분리한다.
  - 과금되는 스크립트는 기본값이 "아무것도 안 함"이거나 상한이 있어야 한다.
  - 실패 확인용 재실행은 호출 없이 캐시만 읽어서 확인한다.

## 2026-11-02 #5. 20m 근접 후보 5건 결정 (승인 3 / 거절 2)

- **날짜**: 2026-11-02
- **발견한 문제**: #2의 20m 규칙으로 검토 대기에 들어온 근접 후보 5건 중 같은 가게와 다른 가게가 섞여 있어 사람이 가려야 했다.
- **원인**
  - 처음 추측: 가까우면(20m 이내) 대부분 같은 가게일 것이다.
  - 실제 원인: 같은 건물·상가 안의 다른 가게도 20m 안에 들어온다. 이름 유사도가 낮은 이유가 "표기가 달라서"(영문 병기)인지 "아예 다른 가게라서"인지는 이름을 보고 사람이 가려야 했다.
- **내가 내린 판단과 요청**
  - 승인: 레이지요거트 강남점, 라운지엑스 24h 강남역점, 스탑오버. 영업시간을 조회(3건).
  - 거절: 옵션스페셜티커피 서초동아타워점 → 카페베네강남동아타워점(8m), 강다짐 강남역지하상가점 → 더벤티 강남역지하상가점(4m). 다른 가게.
- **해결 방법**: `--reject`(조회 없이 `rejected`로 표시, 반영 안 함)를 추가하고, `--approve`로 3건 승인하며 영업시간을 조회했다.
  - 승인한 3건은 이름이 영문·다국어 병기(Lazy Yogurt Gangnam, Gangnam Station Cafe, StopOver)이거나 지점명이 붙은 표기 차이였다. 거절한 2건은 브랜드명이 아예 다르다.
- **결과 숫자**
  - 호출: 영업시간 조회 3건(Details). 상한 `--max-calls 3`으로 제한해서 실행.
  - 승인된 영업시간: 라운지엑스 24h = 7일 모두 24시간(`is_24h` 예), 레이지요거트 = 매일 20:00 마감(심야 아님), 스탑오버 = 월~금 22:00 마감, 토·일 휴무(심야 아님).
  - 캐시 상태(40건): 정상 15 / 승인된 검토 6 / 검토 대기 1(마리김밥) / 영업시간 없음 7 / 매칭 실패 7 / 폐업 2 / 거절 2
- **배운 점**
  - 이름에 "24h"가 있는 가게(라운지엑스)를 구글도 24시간으로 확인했다. 이름 기준 교차 확인이 이번에는 일치했다.
  - 스탑오버는 scope에서 술집인데 월~금 22시 마감, 주말 휴무로 나온다. 술집 영업시간으로는 이상하므로, 구글의 "StopOver"가 정말 같은 가게인지 나중에 다시 볼 필요가 있다. (확인 필요)
  - 20m 규칙은 거절이 필요한 후보를 만든다(5건 중 2건). 자동 승인하지 않는 방침이 맞았다.

## 2026-11-02 #6. 기본 동작을 "아무것도 조회하지 않음"으로 변경

- **날짜**: 2026-11-02
- **발견한 문제**: #4의 남은 허점. 인자 없이 `fetch_google_hours.py`를 실행하면 시험 조회 20건이 나가, 목록만 보려는 실행도 과금 호출이 될 수 있었다.
- **원인**: 처음 추측과 실제 원인이 같았다. `--limit`의 기본값이 20이라서, "아무 인자도 안 줌"이 곧 "20건 조회"였다. 호출 상한(40건)은 있었지만 그 안에서는 호출이 나갔다.
- **내가 내린 판단과 요청**: 기본 동작은 "아무것도 조회하지 않음"으로 하고, 조회는 인자를 줬을 때만 하게 할 것.
- **해결 방법**: `--limit` 기본값을 없앴다(None). `--limit N`, `--limit 0`, `--retry` 중 하나를 줘야만 조회한다. `--approve`/`--reject`는 캐시만 고치고, 승인 시 영업시간이 없는 건에만 1건씩 조회한다. 인자 없이 실행하면 "조회 인자가 없어 아무것도 조회하지 않습니다"를 출력하고 호출 0건으로 끝난다. `--max-calls` 상한은 그대로 둔다.
- **결과 숫자**: 인자 없는 실행 호출 0건 확인. `--approve ... --reject ... --max-calls 3` 실행 호출 3건(승인 3건의 영업시간 조회).
- **배운 점**
  - 과금되는 도구의 기본값은 "안전한 쪽"(아무것도 안 함)으로 둔다. 실행하려면 의도를 인자로 밝히게 한다.
  - 같은 종류의 실수(#4)가 났을 때는 안전장치(상한)에 더해 기본값 자체를 고쳐야 재발하지 않는다.
